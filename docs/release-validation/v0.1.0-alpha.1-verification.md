# `v0.1.0-alpha.1` Post-Release Verification

**Date:** 2026-08-27
**Repository:** `michaelegner/architecture-intelligence-platform`

**Purpose of this document:** verify the `v0.1.0-alpha.1` release artifact itself, and separately
record the corrective changes discovered while validating it. These are two different states —
kept in two different sections below, not blended — because the fixes described in "Post-alpha
fixes verified on `main`" are **not** part of the `v0.1.0-alpha.1` tag or the image it currently
points to. See "Release provenance" for exactly why.

## Release provenance

```text
Git tag v0.1.0-alpha.1
    -> commit 4230f5996dbf4f19377ba3369d92a4d66ee6dd33

Two GitHub Actions `docker.yml` runs fired for this one release (createdAt 09:42:00Z, both):
    -> run 33059746919 (release: published event) -> pushed sha256:109fe5a6fa3ecd35e4ce4313f9779d9d2eba5c0ced4288c19faa5c2d367ecfca  (09:42:28Z)
    -> run 33059746639 (push: tags event)          -> pushed sha256:39bf2336941e8f5ee82c7529172d2859bee13c48d529251e7c27ca5381951b6b  (09:42:34Z, LATER - overwrote the tag)

ghcr.io/.../architecture-intelligence-platform:v0.1.0-alpha.1 and :latest
    currently resolve to -> sha256:39bf2336...
    (sha256:109fe5a6... still exists in GHCR, but untagged/orphaned - confirmed via the package's version list)
```

`docker.yml` had two triggers at the time (`release: published` and `push: tags: "v*"`), and both
matched this one release — a straightforward race, whichever run's push landed last in the registry
wins the mutable tag pointer. This is a real defect in the *release process*, not a description
error: independently reproduced from each run's own logs (`gh run view <id> --log`), not just
inferred from the final registry state.

**Consequence:** both digests were built from the same commit (`4230f599`), so there's no
functional difference between them — but that commit is **13 minutes older** than the non-root
Dockerfile fix (`40e63d9`, committed 11:51:41+02:00 vs. `4230f599`'s 11:38:09+02:00). The
currently-tagged `v0.1.0-alpha.1`/`latest` image therefore **still runs as root**. The non-root fix
below was tested against a locally-built image from a later commit, never against a re-tagged
`v0.1.0-alpha.1` artifact — this document previously implied otherwise, which was wrong.

`docker.yml`'s trigger has since been fixed to `release: published` only (commit `e3e424b`) —
exactly the change that prevents this race. That fix has not yet been exercised by an actual
release; see "What's next" below.

**The `v0.1.0-alpha.1` tag itself is not being moved, rewritten, or deleted.** It did what an alpha
release is for: got tested, and surfaced real defects. Those defects and their fixes are recorded
honestly below as changes to `main`, not folded back into the tag's own history.

## Post-alpha fixes verified on `main`

Everything in this section was verified against the actual repository/infrastructure (a real
GitHub repo, a real Docker daemon, a real Neo4j container) at various commits on `main` following
the alpha release — **not** against the `v0.1.0-alpha.1` tag or its GHCR image specifically, per the
provenance note above.

### CI / CodeQL on GitHub infrastructure

The first time this repository's `ci.yml`/`codeql.yml` ran anywhere other than local `pytest`/`ruff`
was after the initial push to GitHub (before the alpha tag existed). Result: **green on the first
run**. CodeQL found one real finding on that first run — `py/stack-trace-exposure` in
`GET /health/neo4j` (it returned `str(exc)` directly to an unauthenticated caller, which for a Neo4j
driver error could include connection details). Fixed (log server-side, return a generic error
body), pushed, re-scanned: **0 open alerts** since. Every commit on `main` has been individually
re-verified green (CI + CodeQL) before the next change was made, through the current HEAD.

### Fresh-clone Quick Start (re-verified against the literal fixed README, commit `e3e424b`)

An earlier run of this same check used a manually-typed correct clone URL/password, since it
predated the README/`.env.example` fix. Re-ran it for real afterward:

```bash
git clone https://github.com/michaelegner/architecture-intelligence-platform.git
cd architecture-intelligence-platform
cp .env.example .env
docker compose up --build
```

**Zero manual edits** — copied `.env.example` verbatim (`NEO4J_PASSWORD=change-me-local`) and ran
exactly what the README says. `GET /health` → `200`, `POST /api/import` → `200`, a deterministic
analysis and a deterministically-routed natural-language query both work, an unrecognized question
with no `OPENAI_API_KEY` set returns a graceful `503` rather than crashing, and the container runs
as `app` (non-root, confirmed via `docker exec ... whoami`).

**Found and fixed along the way**: `docker-compose.yml` used `${OPENAI_API_KEY:?...}` (hard
required), contradicting the documented LLM-optional guarantee — a fresh clone with a blank
`OPENAI_API_KEY` failed to start at all. Fixed to `${OPENAI_API_KEY:-}`.

### Fresh-clone runtime demo

Clean clone, `docker compose -f docker-compose.demo.yml up --build`, then
`examples/runtime-demo/README.md`'s walkthrough followed exactly:

- Immediately after `POST /api/import`, before any traffic: every declared relation showed
  `NOT_OBSERVED_IN_WINDOW` (`GET /api/analysis/runtime/declared-only?environment=demo`).
- After traffic landed: `order-service → product-service.getProduct` and the `payment-q`/
  `invoice-q` sends/receives showed `CONFIRMED`.
- `OrderService → LegacyPricingService` (never declared anywhere) showed `OBSERVED_ONLY`.
- The 11H reconciliation scenario: removed `order-service`'s `calls` entry, reimported just that
  service, watched `product-service` move from `confirmed` to `observed-only` (not deleted) —
  confirmed via the real API, then restored the fixture.
- Cross-batch correlation: watched the traffic generator's log lines showing a CLIENT span and its
  matching SERVER span sent as two separate OTLP requests, still resolving to one relation.
- The web UI (`/services/service:order-service`, `/query`) shows the same states.

**Found and fixed along the way**: the natural-language query page (and any O1-O5 API call without
an explicit `environment` param) silently returned zero rows against demo data, because
`config.yaml`'s `runtime_analysis.default_environment` (`production`) didn't match the demo's own
`environment=demo` traffic tag. Fixed with a demo-specific `config.demo.yaml`
(`docker-compose.demo.yml`'s `CONFIG_PATH`).

### GHCR image — pulled and run from a clean environment

```bash
docker pull ghcr.io/michaelegner/architecture-intelligence-platform:v0.1.0-alpha.1
```

Run against a freshly-started Neo4j container (no local source checkout at all — just the published
image): container starts, connects to Neo4j, `GET /health` and `GET /health/neo4j` both return
`200`.

**Confirmed genuinely public**, not just API-reported: `docker logout ghcr.io`, deleted the local
image, pulled again with **zero credentials** — succeeded.

**Found and fixed along the way**: the container ran as `root` (`docker exec ... id` →
`uid=0(root)`) — no `USER` instruction in `Dockerfile`. Fixed on `main`: dedicated `app` user
(uid/gid 1000), `COPY --chown`, `USER app` before `CMD`. Re-verified end-to-end **against a locally
built image from the fix commit** — `docker exec ... whoami` → `app` — both standalone and via
`docker-compose.demo.yml` (which bind-mounts `examples/` and `config.demo.yaml` from the host;
host-owned files stayed readable to the non-root user under standard world-readable permissions, no
breakage). This has **not** been re-verified against a pulled, tagged GHCR image yet — that's exactly
what `v0.1.0-alpha.2`'s verification (below) is for.
